## 4. Melhorias de arquitetura para decisão do usuário

### Proposta 1: persistência atrás de um store único, escolhido uma vez
- **Problema atual:** há 24 ramos `if (!isSupabaseConfigured())` espalhados em 4 serviços. As regras (estrelas, desbloqueio da próxima fase, mundo completo, nível por XP) estão escritas só no ramo local. O ramo Supabase divergiu: não filtra por aluno, usa ids falsos e não lê progresso (achados 1, 2 e 13).
- **Proposta:**
  ```
  src/lib/store/
    progressStore.ts       // interface ProgressStore { loadLevels(age), saveLevel(age,n,data), addXP(n), ... }
    localProgressStore.ts  // código atual do localStorage
    supabaseProgressStore.ts
    index.ts               // export const store = isSupabaseConfigured() ? supabaseStore : localStore
  ```
  Antes: `completeLevel` mistura regra e I/O nos dois ramos. Depois: `completeLevel` calcula estrelas, desbloqueio e mundo uma única vez e chama `store.saveLevel(...)`.
- **Benefício:** uma só versão de cada regra, testável com um store fake em memória, e o modo Supabase recebe as mesmas regras de graça.
- **Custo/risco:** é preciso tornar assíncronas as funções que hoje são síncronas (`getLevelProgress` é usado no render de `AdventureMapPage` e `WorldSection`).
- **Esforço:** médio. Dá para fazer de forma incremental, um serviço por vez, começando pelo `adventureService`.

### Proposta 2: code splitting por rota e dados por faixa etária
- **Problema atual:** um chunk único de 1,37 MB. As 13 páginas são importadas de forma eager em `App.tsx:5-16`, e as 6.610 linhas de `adventureActivities.ts` com todas as faixas entram no bundle inicial.
- **Proposta:** `const TeacherDashboardPage = lazy(() => import('./pages/TeacherDashboardPage'))` com `Suspense` na raiz, e `ADVENTURE_ACTIVITIES` dividido em um arquivo por faixa, carregado com `import(\`./adventure/${age}.ts\`)`.
- **Benefício:** carregamento inicial bem menor em aparelhos fracos. O recharts e os dados das outras faixas só baixam quando são usados.
- **Custo/risco:** `activityService.getActivityById` passa a carregar a faixa antes de buscar. O script `auditActivities.ts` precisa importar todas as faixas.
- **Esforço:** baixo para as rotas e médio para os dados. Totalmente incremental.

**Minha recomendação:** primeiro, decida se o modo Supabase vai para produção. Se for, faça a Proposta 1 primeiro: hoje esse modo perde dados e pode apagar o progresso de todos os alunos. Se não for, remova os ramos Supabase incompletos, o que elimina os achados 1, 2 e 12 e simplifica o código, e faça a Proposta 2, de baixo esforço e ganho direto para o público.

Qual proposta você quer seguir: 1, 2 ou nenhuma? E o modo Supabase vai para produção?
